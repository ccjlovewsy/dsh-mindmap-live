# 需求拆解：画布提问 → 会话直答

> 状态：需求拆解（P0 技术风险已排除，待排期） ｜ 日期：2026-09-29（2026-09-30 spike 结论回填） ｜ 目标插件：`@dsh-external/dsh-mindmap-live`
> 一句话：用户在思维导图画布上以节点形式提出问题，AI 在**当前会话**里直接拿到这个问题并回答，答案再回到画布上。

---

## 1. 背景与现状速览

当前插件（v0.0.1）的架构决定了"提问—回答"两段链路的可行性边界：

| 组件 | 位置 | 与本需求的关系 |
|---|---|---|
| 共享树状态 | 宿主 `src/index.ts`（内存 + `~/.dsh/dsh-mindmap-live/tree.json` 落盘，version 单调递增） | 提问节点和回答节点都存在这棵树上 |
| 变更管线 | `POST /op`（client 画布与 AI 工具走同一条） | 用户"提问"和 AI"写答案"天然同管线，无需新通道 |
| AI 工具 | `mindmap_get` / `mindmap_edit`（`src/index.ts:308/335`） | AI 读题、写答案的能力**已经存在** |
| 画布 | `src/client/MindmapCanvas.tsx`（SSE + 2.5s 轮询兜底） | 提问入口的 UI 载体；且**本身实时同步，不需要"刷新"** |
| 会话交互权 | AI 只能在"收到用户消息"后行动 | **本需求的核心难点**：谁、通过什么方式让会话开新一轮 |

关键认知：AI 侧"读题 + 答题 + 写回画布"的能力已齐备，缺的只是**从画布到会话的触发通道**。

## 2. 用户故事

- **US-1**：我在画布上选中一个节点，输入"为什么会冷启动崩溃？"，点「问 AI」→ 当前对话里自动出现这条提问 → AI 回答，并把答案作为子节点挂回该问题下。
- **US-2**：我直接新建一个以 `？` 开头的节点（约定标记）→ 下一次我回到对话时（或面板自动触发），AI 主动看到这个问题并回答。
- **US-3**：一个问题只回答一次；回答过程中节点显示"回答中"；完成后显示"已回答"。

## 3. 核心链路拆解（四段）

```
[标记提问] → [感知] → [触发会话] → [回答 + 回写画布]
```

### 3.1 标记提问（提问如何表达）

| 候选 | 说明 | 评价 |
|---|---|---|
| A. 右键/按钮「问 AI」 | 选中节点 → 工具栏或右键菜单点「问 AI」→ 弹小输入框补问题（默认带节点标题） | ✅ 意图明确、无歧义，P0 首选 |
| B. 约定前缀 | 节点标题以 `？`/`?`/`问：` 开头即视为提问 | 适合作为 P1 的"自动触发"补充；歧义风险（正常内容可能以？开头） |
| C. 独立提问输入框 | 面板顶栏一个输入框，问题不进树、直接进会话 | 简单但脱离导图语境，弱化"导图即工作区"的定位；可作 P1 附加 |

### 3.2 感知（谁发现"有提问"）

| 候选 | 机制 | 评价 |
|---|---|---|
| A. client 感知 | 画布在用户点「问 AI」的**当下**直接发消息，无轮询 | ✅ 实时、零延迟、无多余扫描；P0 |
| B. host `/op` 钩子 | 宿主在处理 ops 时识别"提问类 op"，记 pending 队列 | 为 P1 自动触发铺路；P0 不需要 |
| C. 轮询扫描 | 定时扫全树找未回答问题 | ❌ 浪费且延迟高，不采纳 |

> 澄清需求原文里的"思维导图刷新后"：画布本就通过 SSE 实时同步，**该链路不需要刷新页面**；"刷新"只影响浏览器加载的 client 代码版本（改代码才需要）。

### 3.3 触发会话（核心难点：让 AI 开口）

| 候选 | 机制 | 可行性 | 评价 |
|---|---|---|---|
| **A. client 直发消息（推荐 P0，spike 已验证 ✅）** | 画布把问题组装成一条普通用户消息发进当前对话（带 `[来自思维导图 nodeId=… v=…]` 前缀与上下文路径） | 通道已确认：`ctx.sessions.binding(sessionId).session.prompt()`，与聊天输入框同一通道（见 §7.1） | ✅ 零宿主改动；消息进会话日志，天然可追溯 |
| B. host 注入用户 turn | 宿主插件直接向 agent 会话注入一条合成用户消息 | ⚠️ 需 spike：探明 DSH 是否允许宿主插件发起 agent turn、权限边界 | 破坏"用户消息由用户发出"的语义，容易形成自动风暴；列为 P2 研究 |
| C. daemon 自答 | 宿主起守护循环轮询问题并自动调 LLM | 技术上可行（参考 daemon-loop 形态） | ❌ 绕过会话，答案不留在对话里，用户失去上下文 |

### 3.4 回答 + 回写画布

1. AI 在会话里正常生成回答（用户可继续追问，上下文完整）；
2. AI 调 `mindmap_edit` 把答案作为**子节点**挂到问题节点下（title 约定前缀 `答：` 或引入节点元数据）；
3. 问题节点标记状态，画布上渲染角标。

**状态机**（挂在问题节点上）：

```
(无标记) --用户点「问AI」--> pending --AI开始写答案--> answering --写完--> answered
                             |                                          |
                             +-------- 用户取消/删除节点 ----------------+
```

## 4. 数据模型增量

当前 op 只有 `title/children/collapsed`，需要二选一：

- **方案甲（P0，零 schema 改动）**：纯 title 约定——问题节点前缀 `❓`，答案子节点前缀 `✅`；状态用前缀切换表达。
  - 优点：`mindmap_edit`/`/op` 管线一行不改；缺点：约定脆弱、程序判断靠字符串匹配。
- **方案乙（P1+，扩展 op）**：节点增加可选 `meta` 字段（`{ kind?: 'question', status?: 'pending'|'answering'|'answered', askedAt?, answeredAt? }`），`/op` 与落盘结构同步扩展；画布按 `meta` 渲染角标。
  - 需要：`addNode/renameNode` 支持 meta、`state` 透传 meta、旧树兼容（无 meta 视为普通节点）。

**推荐**：P0 用甲快速验证闭环，P1 切乙。

> P0 状态降级说明：方案甲只有 `❓`（pending）/ `✅`（answered）两态；US-3 的"回答中"中间态 P0 不表达（`❓` 即"已送答、等待回答"），P1 引入 meta 后补齐。

## 5. 防御性设计（必须写进验收）

1. **去重**：同一问题节点只在 `pending/answering` 状态时可触发一次；`answered` 后「问 AI」按钮置灰。
2. **防循环**：AI 写回的答案节点不得再被自动触发提问（答案节点 `kind !== 'question'`；title 前缀方案里 `✅` 开头不参与匹配）。
3. **失败路径**：会话发送失败 / AI 超时未写回 → 节点退回 pending 并显示重试入口；禁止静默吞错。
4. **并发**：用户在 AI 回答期间手改问题节点标题 → 以提交提问时刻的快照为准，回答节点挂当时的问题节点 id 上（id 稳定，改标题不影响挂载）。
5. **多会话**：树是全局的，但触发走"当前会话"；同一问题被两个会话先后回答 → 后者覆盖答案节点前，先弹出确认（P1 再做，P0 允许后写覆盖）。

## 6. 分期落地

| 期 | 内容 | 涉及面 |

| **P0 最小闭环** | 工具栏「问 AI」按钮（选中节点可用）→ 组装消息发进当前会话（含问题节点 id 与标题路径）→ AI 用 `mindmap_edit` 写「答：」子节点 → 问题节点 title 前缀切换 `❓→✅` | 仅 client + 一段提示词约定；**零宿主改动** |

## 7. 开放问题（实现前需确认）

1. ~~client 侧向会话发消息的**现有通道**是什么~~ **✅ 已关闭（2026-09-30 spike：存在正式通道，零新增 API）**：
   - 调用链：client `apply(ctx)` 闭包捕获 `ClientContext` → 槽位 props 自带 `sessionId`（conversation.view 是 session 作用域槽位）→ `ctx.sessions.binding(sessionId)?.session.prompt([{ type: 'text', text }], 'queue')`；
   - 依据：`packages/client/runtime/src/client/contract/session.ts`（`ISession.prompt` 注释 "Send a prompt into the session"）；`packages/client/ui-conversation/src/client/service.ts:131`（聊天输入框自己就是这样发的）；`packages/client/ui-slots/src/renderer.ts:62`（session 槽位标准套件注入 `sessionId`）；
   - 附带约束：client `inject` 数组需加 `'sessions'`；mode 固定 `'queue'`（`'steer'` 是打断当前轮，提问场景不用）；返回 `RpcResult`，`ok === false` 时走 §5.3 失败重试路径。
2. AI 侧提示词约定放哪：`mindmap_edit` 的 tool description 里追加"收到 [来自思维导图] 消息时的应答规范"，还是单独 system-prompt 注入。
3. 答案很长时画布节点的展示策略（截断 + 全文锚点跳转会话消息）。

## 9. P0 最小步骤拆解与逐步验证（第一性原理）

原则：每步只做**一件可独立验证的事**；自动验证优先、人工验收兜底；**当前步全绿才进下一步，红了先修，禁止带着红状态写下一步代码**。

消息契约（S2 发、S4 认，模板定死，双方不得各自发挥）：

```text
[来自思维导图 nodeId=<节点id> v=<发送时version>] <问题文本>
```

`v` 的用途：AI 应答时发现 version 已变，先 `mindmap_get` 重读再挂答案（§5.4 的并发防线）。

验证基线命令（每步前后都要全绿）：

```bash
npm run typecheck          # tsc --noEmit
bash scripts/build.sh      # host tsc + client tsdown + npm pack
B=http://127.0.0.1:3080/@dsh-external/dsh-mindmap-live/api
curl -s $B/state           # 运行态树结构断言（热装配后）
```
